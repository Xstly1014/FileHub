# FileHub 完整实现计划（从原型到全功能跑通）

> 制定日期：2026-08-17
> 目标：**30 个功能（E1–E10 + C1–C20）全部真实跑通**，前后端闭环，Docker 一键启动。
> 依据：[API_AUDIT.md](./API_AUDIT.md)（现状审计）、[FEATURES_PRD.md](./FEATURES_PRD.md)（功能规格）
> 已确认决策：① 前端**演进现有零依赖原型**（不重写 React）；② **本地单机优先**（单用户为主，协同做到"可演示的真实"，不追求生产级多租户）。

---

## 一、总原则

1. **先闭环，后繁荣**：主链路（登录 → 上传 → 画布 → 编辑 → 版本 → AI）不通之前，不碰创意功能。
2. **消灭假接口**：每个端点要么真实实现，要么显式 501，不允许写死假数据冒充 200。
3. **每个里程碑可验证**：每阶段结束有明确的验收清单，用浏览器 + curl/pytest 双验证。
4. **前端保持零构建**：继续原生 JS + hash 路由，但收敛为**单一 API client**（`js/api.js`）+ **单一状态层**。
5. **硬约束**：所有资源只写 D 盘；密钥只进 `backend/.env`，前端无密钥；仓库只推运行必需文件。

## 二、最终架构（目标形态）

```
浏览器（原生 JS 原型，端口 8080）
  ├─ js/api.js      唯一 API 客户端（401 自动刷新重放 / 离线写队列）
  ├─ js/store.js    新增：单一状态层（文件/画布/标签/通知，替代散落的 App.data）
  └─ js/ws.js       新增：WebSocket 客户端（鉴权 / 重连 / 事件分发）
        │ HTTP + WS
FastAPI 后端（端口 8787，/api/v1）
  ├─ auth / workspaces / files / canvas / tags / comments / shares ...
  ├─ AI 层：LangChain Runnable（chat/summarize/tags/links/dedup/health）
  ├─ 解析队列：上传 → 文本抽取（PDF/DOCX/MD/代码/图片 OCR 占位）
  └─ SQLite(WAL) + FILES/ 磁盘存储 + Qdrant 向量库
Docker Compose：web(nginx) + api + qdrant
```

新增文件控制在最小集：`js/store.js`、`js/ws.js`、`backend/` 内按域拆分路由模块（`routers/*.py`）+ `tests/`。

## 三、阶段计划

### M0 · 安全止血（先于一切）

对应审计 P0 项。**不完成 M0 不允许暴露端口。**

| ID | 任务 | 验收标准 |
|---|---|---|
| M0-1 | 吊销 `.env.example` 中的真实密钥，改为 `replace-me` 占位 | 文件内无任何真实密钥 |
| M0-2 | `FILEHUB_JWT_SECRET` 未配置时启动即报错退出 | 无 secret 启动失败并有明确提示 |
| M0-3 | 修复 refresh 流程：refresh token 改为 DB 比对 + 支持轮换 | 前端用 refreshToken 能换新 accessToken |
| M0-4 | WebSocket 握手鉴权（query 带 token，失败 close 4401） | 无 token 连接被拒 |
| M0-5 | `GET /api/exports/{name}` 加 Bearer + 归属校验 | 他人/匿名访问 404 |
| M0-6 | 分享访问校验 `expires_at` 与 `permission` | 过期分享返回 410 |
| M0-7 | 上传大小限制（默认 100MB）+ `rmtree` 路径白名单（只许 `FILES/{fid}`） | 超限返回 413；导入文件 purge 不再触碰 cwd |
| M0-8 | AI base_url 去掉硬编码公网 IP 默认值，未配置时 AI 走显式 fallback | 无配置不产生外发请求 |

## 五、依赖与顺序约束

```
M0（安全）→ M1（正确性）→ M2（主链路）→ ┬→ M3（AI）→ M4（图谱洞察）
                                          └→ M5（协同分享）
                                          └→ M6（体验收尾，可并行穿插）
```

- M3 依赖 M2-4（上传链路）与 Qdrant 容器；M4 依赖 M3-2（向量）中的去重/关联部分。
- M5 依赖 M2-5（画布持久化）。
- M6 各任务相对独立，可穿插在其他阶段间隙做。

## 六、每阶段验证方式

1. **后端**：`pytest` + 手工 curl 关键端点；启动 `uvicorn` 后过一遍 `/docs`。
2. **前端**：浏览器按各阶段验收清单逐项点击验证（用户偏好端口 8080，占用则先杀进程）。
3. **集成**：`docker compose up -d --build` 后从 `http://localhost:8080` 走完整用户旅程：注册 → 上传 PDF → 等待解析 → 画布连线 → 编辑保存 → AI 问答 → 分享 → 导出。
4. 每完成一个阶段，在本文档对应任务后打勾，并把结论追加到 `.workbuddy/memory/`。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| LLM 服务不稳定（第三方 base_url） | 所有 AI 路径保留显式 fallback + 超时；M3 完成前先验证密钥可用性 |
| PDF/DOCX 解析质量差 | 解析失败标记 `failed` 并允许手工粘贴文本，不阻塞主链路 |
| 原生 JS 规模膨胀难维护 | store.js 单一状态层 + 按视图拆文件；必要时 M6 后评估是否引入构建 |
| SQLite 并发瓶颈 | WAL + 单用户场景足够；预留迁移 PostgreSQL 的 alembic 路径 |
| 范围蔓延 | 严格按阶段验收，新想法先记入 BACKEND_TODO.md 不打断当前阶段 |
